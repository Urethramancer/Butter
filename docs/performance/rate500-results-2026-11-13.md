# Focused 500 Mbps CPU work

## Baseline attribution

All four partial trials validate: two Instruments captures and two separate
operation-counter diagnostics. The 4 GiB, 128-file hybrid fixture uses 256 KiB
pieces and a seed-side loopback limit. The diagnostic interval runs from transfer
start through the durable shutdown gate, including settle, measurement, drain
and persistence. Comparison metrics use only the ten-second window after five
seconds of settling. Instrumented samples are excluded from comparisons.

Butter's capture contains 4,872 Running samples. These disjoint executing-leaf
categories describe calling stacks, not measured kernel residence time:

| Work | Running sample weight |
| --- | ---: |
| Filesystem metadata/open/close | 39.29% |
| Payload I/O | 9.42% |
| Networking | 3.82% |
| Scheduling and event delivery | 3.02% |
| Kernel-facing copying (`vm_copy`) | 2.67% |
| User hashing | 14.86% |
| User copying/clearing | 4.02% |
| User allocation | 2.79% |
| Other processing or unresolved execution | 15.72% |
| Unattributed | 4.39% |

The largest open stack, 13.20%, is `openat` beneath `StorageDirectory.parent`,
`inspect` and `writeOperations`. Another 10.47% is close beneath write cleanup;
2.73% is open beneath the batch's initial target inspection. These are separate
sample stacks, not overlapping inclusive totals. The separate counter run
records 72,931 directory opens, 9,708 payload-file opens, 51 atomic-state opens,
85,816 descriptor duplications and 110,204 descriptor inspections. Its 6,478
write batches contain 50,248 blocks, with 43,750 descriptor-cache hits. Both
hashes process 823,132,160 bytes. Counts cover start through durable; they are
not timing results or directly equal to the differently instrumented capture.

`mach_msg2_trap` includes 1.95% under `vm_copy` in peer input appending and
0.72% under `vm_copy` in storage reads. These are copying stacks, not evidence
of time spent waiting for disk or worker scheduling. Direct storage dispatch
under `__workq_kernreturn` accounts for 0.21%; continuation resumption includes
0.37% with mixed ancestry. Worker ancestry's 71.8% inclusive weight describes
where work executes and is not scheduling overhead. No combined-write/verify
candidate is justified by this capture.

Filesystem inspection remains the largest opportunity, but its dominant path
matches the previously rejected descriptor/parent-cache experiments. There is
no materially different, evidence-supported cache change within the required
replacement, symlink, hard-link, permissions and external-edit protections.
This area is exhausted for this pass; this does not establish that filesystem
optimisation is impossible. Scheduling is likewise exhausted on current evidence.
Hashing/copies receive one isolated direct-leaf-range trial below.

## Rejected direct leaf hashing

The isolated candidate hashed each existing 16 KiB byte range through CryptoKit's
buffer-pointer update instead of allocating a Data copy for every SHA-256 leaf.
No filesystem, batching, picker, persistence or request-limit behaviour changed.
The comparator is production source `27247f3`, with one identical current driver
source compiled against both packages and one native binary throughout.

All 28 samples validate independent partial pieces and reopened checkpoints:
one warm-up per source/engine and six fixed balanced source pairs at 500 Mbps.
Every sample meets the existing saturation/ceiling safeguards. No counters,
profilers, builds or tests ran concurrently with timing; process checks observed
no competing builds/tests/profilers. Other-project Xcode tests were allowed to
finish before comparison preparation. There were no retries or extra pairs.

| Candidate/parent | Median | Paired 95% interval |
| --- | ---: | ---: |
| Total CPU s/GiB | 1.0042 | 0.9049–1.0715 |
| User CPU s/GiB | 0.9816 | 0.9063–1.0588 |
| System CPU s/GiB | 1.0183 | 0.9040–1.0797 |
| Payload MB/s | 0.9997 | 0.9722–1.0006 |
| Peak RSS | 0.9973 | 0.9782–1.0146 |
| Counterpart CPU s/GiB | 0.9993 | 0.9757–1.0391 |

No CPU component establishes an improvement. Throughput and counterpart CPU
also remain inconclusive; peak RSS meets the 10% allowance, including the
maximum-peak check (ratio 1.0). Native-control CPU is likewise noisy, with ratio
1.0100 [0.7208–1.3233]. These data do not establish a source regression or a
speed-up. The candidate is reverted because total CPU's upper interval is not
below one. The fixed sample budget is final.

## Final shutdown capture and restored source

The final profile mode keeps the tested driver alive at `stopped` until Instruments
has finished. Both engines' final partial trials validate, with capture extending
through actual engine/storage/session shutdown rather than the earlier durable
gate. This is diagnostic verification of the profiling protocol, not another
source comparison. All production Swift source hashes match the comparison's
parent exactly; the direct-leaf implementation is absent.

The restored Butter capture contains 5,319 Running samples: filesystem
metadata/open/close 41.25%, payload I/O 10.10%, hashing 14.83%, user copying
3.95%, kernel-facing copying 2.71%, allocation 2.14%, networking 3.46% and
scheduling/event delivery 2.59%. Other/unresolved execution is 15.06% and
unattributed execution 3.91%. These disjoint categories confirm the earlier
attribution. Individual direct write/verification submission stacks are 0.19%
and 0.06%; a storage completion-resumption stack is 0.34%. They provide no
new evidence for a distinct combined-worker or filesystem-cache experiment.
